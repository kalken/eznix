# CLAUDE.md

Guidance for Claude Code sessions working in this repository.

## The most important rule: general solutions, never hardcoded

The editor handles data it cannot know in advance: any option of any module, any name, any nesting, any theme, most of it never looked at by anyone. So every fix and feature is made for the *kind* of thing, not the one on screen.

- No code that names an option, a section, a file, a plugin or a theme.
- No branch per kind of row where one rule can cover them all; take what differs from the element itself (the rename field inherits its font and colour from the name it covers).
- The page reaches plugins only through events, never by name. Suggestions are read by their form, never by an option's name.
- If a fix only works for the case in the report, it is not done. Before finishing, ask what else it would hit, and try it on a different kind of data.

## Keeping this file short

This file says how the code is put together and which rules to follow. It is not a log.

- No dates, no "the user said / tried / saw", no commit hashes, no test reports, no lists of what was or was not verified. History is in `git log`; the reasons are in comments next to the code.
- A new entry is a few lines: the rule, and the one reason that stops someone from undoing it. If a change fixes a bug, the fix goes in the code and its comment, not here.
- Something the user turned down gets one line ("don't build X") only if it would otherwise be suggested again.
- Nothing about one person's machine (paths, flake, what their computer runs): this file is checked in and public.

## Git

Work is committed to `develop`; `main` is what the repository shows and what `github:kalken/eznix` gives (the templates, the installer). A machine that wants what is not released yet names `github:kalken/eznix/develop`.

- Always commit to `develop` first. Only merge `develop` into `main`; never commit to `main`.
- Do not commit unless asked. Until then a change stays in the working tree, and the report says it is uncommitted.
- Do not push unless the user says so in that turn. Committing is not a go-ahead to push.
- Do not add Claude as co-author in commit messages.
- The installer ISO is built and released by hand: ezinstall's Actions, "Build ISO", or "Tell ezinstall" here (`.github/workflows/ezinstall.yml`, a `repository_dispatch` with the commit, token in the secret `EZINSTALL_TOKEN`).

## Workflow

Don't use subagents for work in this repo. Don't test in a real browser (headless Chrome, CDP) unless the user asks for it in that turn.

**Local test server.** After any change the user can see (`webroot/`, `plugins/`, `bin/eznix.py`), restart it before reporting back, without being asked. Its data lives outside the checkout, in `../.eznix-test/` (`eznix.toml`, state, usually a flake; read `eznix.toml` instead of assuming what it points at). Never run `nix build path:.` inside it: that copies the test state, keys included, into the store. **The test server never points at a flake a real machine builds from**, only a copy or a throwaway flake: a save or import there changes what that machine builds next.

```sh
pkill -f "eznix.py --config eznix.toml"; sleep 1
(cd ../.eznix-test && PYTHONUNBUFFERED=1 nohup python3 ../eznix/bin/eznix.py --config eznix.toml --dev >| server.log 2>&1 &)
sleep 2; curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:9690/api/v1/ping   # 401 = up
```

- http://127.0.0.1:9690, password `eznix`. It starts its own terminal on port 9691, so a restart restarts the shell too.
- With `--dev` the server rereads the page, themes and plugins when they change and an open tab reloads by itself; only `bin/eznix.py` needs a restart.
- The `pkill` only matches a server started with exactly that `--config`. A server started with another file keeps the port and keeps serving the old page, the new one fails to start, and the 401 still comes back. If in doubt, see what holds the port (`lsof -nP -iTCP:9690 -sTCP:LISTEN`), restart that command line, and check that the served file has the change.
- The Autocomplete button, run from a checkout, types `python3 .../bin/eznix-autocomplete.py --flake FLAKE --output STATE/autocomplete` into the terminal (`_autocomplete_command()`).

**Checks.** Nothing tests the page's own scripts. At least syntax-check them after editing: without `node`, a Mac can parse and run a function lifted out of them with `osascript -l JavaScript file.js` (wrap a script in `new Function(source)` to check syntax only; don't name a function `run`). `python3 test/test_server.py` checks the server and the plugins' server halves against a throwaway flake: run it after touching `bin/eznix.py` or a plugin's `.py`. It does not cover anything in the page.

## Documentation

When a change adds, removes or changes what a user sees or sets, update `README.md` (for users) as well as this file. `example/eznix.example.toml` lists every setting.

`README.md` is the one document for users, laid out like the user's other repositories (ezconf, ezinstall): name and a line on what it is, `## ✨ Features` as a short list, `## 🚀 Quick Start`, a section per topic with an emoji in its heading, `## 📋 Options` and `## 📝 Notes` near the end, and a closing line in italics. Quick Start is what it takes to get eznix installed and running, for people who don't know Nix: three blocks of lines to copy and three steps for using it. Keep it short; new material goes in the sections after it. A link to a section has the emoji's place as a hyphen (`#-https`), and the emoji in a linked heading must be one character with no variation selector. Don't split it into two documents.

Most of the *why* lives in comments next to the code, on purpose: many record an approach that was tried and reverted, and what broke. Read them before changing the thing they sit on, and keep them when moving code.

## What this is

A web editor for Nix configuration: NixOS, nix-darwin and standalone home-manager. It edits `*.json` files in one folder inside the user's flake (`config_dir`, default `<flake>/eznix`), each file a tab, merged at evaluation time by `nix/json2nix.nix`, which the flake imports as `eznix.lib.jsonDir ./eznix`. No build step, no framework, no dependencies beyond Python's standard library (`python-pam` for system-password login and `cryptography` for `--generate-ca` are optional). It replaces an earlier project, ezconf, which ran as root; there is no compatibility with ezconf's configuration.

| | |
|---|---|
| `bin/eznix.py` | the server, one file: static files, the API, logins, the terminal proxy, plugin loading |
| `bin/eznix-terminal.py` | the terminal: a PTY behind a WebSocket, a separate process per user |
| `bin/eznix-autocomplete.py` | generates the suggestions (`nix eval` over the flake) and runs the generator plugins |
| `webroot/index.html`, `style.css` | the page: one script, no modules |
| `webroot/theme-*.css` | themes: variables only (see `THEMES.md`) |
| `webroot/terminal-panel/` | the terminal's part of the page, with xterm.js |
| `plugins/NAME/` | shipped plugins: `documents`, `files`, `system`, `password`, `nixedit`, `uploads` (page files, server file, `README.md`); `kernels`, `homebrew`, `home-manager` hold only a generator file |
| `nix/` | packages, the options shared by the modules, one module per system |
| `templates/` | a starting flake per system, for `nix flake init -t` |
| `test/test_server.py` | server tests; `test/json/` is a folder for `checks.json-dir` |

## Rules for the code

**Nothing is root.** The editor is reachable from a browser, so it runs unprivileged everywhere; a rebuild goes through `sudo` in the terminal. On NixOS an unprivileged service gets two things narrowly: a setuid helper that only checks a password for the listed users (`auth_helper`, a small C program, `nix/eznix-auth.c`: nixpkgs-unstable refuses a wrapper target that is not an ELF binary), and a sudo rule that only restarts the terminal units (`terminal_restart`).

**Nothing from a file or a module goes into the page as markup.** A script in the page can use the whole API and the terminal, which is a shell as the user. Every value from a `.md` file, an imported JSON key, or a module's description, default, example or type goes through `_escHtml()` before `innerHTML`; `parseMarkdown()` escapes `<` outside code and allows only `http(s)`, `mailto` and scheme-less links (`safeUrl()`). A new `innerHTML` with a value in it needs `_escHtml()`. Under that there is a `Content-Security-Policy` (`_csp_scripts()`, `_csp_header()`): scripts only by hash, computed at render time for every inline `<script>` and every `onclick="..."`-style attribute written in the page or in a script file that puts markup in it. **A handler built from a variable or by concatenation is not found by the scan and is blocked**: write it as a plain string or set `el.onclick = fn`. Answers carry `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`. No `Referrer-Policy: no-referrer`: it makes a browser leave `Origin` off same-origin POSTs, which `_valid_origin()` goes by. `test_server.py` checks that everything inline is in the policy.

**Requests must come from the page.**
- `_valid_origin()`: every POST, the login and the `/terminal` handshake are refused when `Origin` names another address than the `Host` the request was sent to, port included (a page on another port of the same host counts as the same site for `SameSite=Strict`). `hosts` is not used for it except an entry that is a whole origin (`"https://name"`, for a proxy that changes `Host`). `"*"` in `hosts` opens the host-name check only.
- `_wrong_host()`, first in `do_GET`/`do_POST`/`do_HEAD`: a host name eznix was not told of gets a 403 saying which name to add to `certNames`, against DNS rebinding. A plain IP address is not a name (`_valid_host()`).
- `/logout` is a POST. No GET changes anything; one that did would need the Origin check.
- A POST has a size (`_body_too_big()`): 16 KiB for the login, 64 MiB for the API, 512 MiB for a plugin.
- Tries at a system password are not locked out per user (it would let anyone who can reach the page lock the real user out); a web login is limited per address (`LOGIN_MAX_ATTEMPTS`) and PAM's own delay stays.

**Paths.** Anywhere a request's value becomes a path it is resolved (`realpath`) and must lie inside its folder; a plugin's `.py`, `plugin.json` and `README.md` are never served (the check is in lower case); the file and folder calls (`_config_path()`) refuse dot-folders and act on a link as the link; the suggestions' file route answers 204 for a missing file and nothing for one outside its folder. The system import refuses entries with `..`, an empty or dot part, and any zip with a path resolving outside the flake.

**Private files are written closed.** Private keys `0600` (`_write_private()`), certificates and backup folders/files `0644`/`0755` (`_write_public()`, `_closed_folder()`), whatever the umask: the NixOS service runs with `UMask = 0002`. In `test_server.py` (`private_keys()`, `backups_closed()`).

**The suggestions generator** never writes or reads through a link in the shared suggestions folder: `.generating` is made with `O_EXCL | O_NOFOLLOW`, files are written under a `mkstemp` name and moved over, `choices.json` is read with `O_NOFOLLOW`.

**Nix expressions** (`_expr`) go through `builtins.toFile`, which fails under `nix flake check`'s read-only evaluation; a rebuild is unaffected, so `checks.json-dir` covers the function without `_expr`. A raw expression gets every module argument (`config`, `options`, `specialArgs`).

## The terminal

- **A separate process per user, on 127.0.0.1.** The browser never connects to it: `_proxy_terminal()` relays `/terminal` after its own login check, replacing the browser's cookie with that terminal's own secret (`key_file`). Each user has their own secret. The terminal never creates the secret; whoever starts it does, before it starts. The key is compared in constant time.
- **NixOS keys:** the user's own file (mode 600) with an ACL entry for the account `eznix` alone (`setfacl -m u:eznix:r`); not group-readable, since every user in `users` is in the group `eznix`. The key's folder (`/run/eznix-terminal/USER`) is root's, mode 755, and only the key file is the user's: the start step runs as root, and a user-owned folder would let a symlink make root `chmod` or create things. The step takes the folder over first and removes a key that is not a plain file. The unit stops if `setfacl` fails.
- **Run by hand**, eznix starts its own terminal as a child (`_start_terminal_for_self()`), writing the key first, registered for whoever logs in (`TERMINALS['*']`).
- **History on reconnect:** up to 5000 lines, kept as rendered text with colours (`_VirtualScreen`, `_scrollback`) and sent ahead of the screen. It is not a replay of raw output. A program's mouse and bracketed-paste modes are kept (`_KEPT_MODES`).
- **Several shells:** the terminal program holds named sessions (`_SESSIONS`, `/terminal?session=NAME`, at most eight); the unnamed one is the panel's. A page asks for one with `eznix.emit('terminal', { el, session, run, onExit })` (`_extraTerminal()`). `run` is started directly, not typed at a prompt. Closing a named shell ends it (the `end` message), never the panel's.
- **A button can run in a tab** (`separate`, `auto_close`; `_runInTab()`, `_openTermTab()`): a named shell in the panel's body, named by a hash of label and command, so a second press fronts the tab. The tabs shown are the terminal's live `tab-*` shells, not this browser's list (`/terminal/hash`, `terminal_tabs` in the ping, `_syncTermTabs()`), so every browser shows the same; which tab is in front stays per browser. A tab is closed for being unlisted only after it was listed once.
- **Copying out:** use `_toSystemClipboard()` (a hidden-field fallback works over plain http, where `navigator.clipboard` is missing). A program's OSC 52 write is handled (`_termOsc52()`); a read (`?`) is dropped on purpose.
- **The panel comes up in front of the editor and takes no room from it** (`.terminal-slot`, `--covered-below`): its place in the page is its row of buttons. The editor gets as much room under its last line as the open panel covers, and that room is not taken back while any of it is on screen (`covered()`), or the file would jump.
- **The terminal's size** is 25, 50, 75 or 100% of the editor area (the window less the bars), 50% unless set: one button that lists them (`showTerminalSizeMenu()`) and a drag of its top edge that catches on the same sizes (`snap` of `eznix.resizable()`). Not one button per size, not bigger/smaller steppers, not one that cycles.
- **The hidden terminal keeps its latest lines in view** (`terminalHiddenLines`, 1 unless set, 0 for none, at most 20; `#term-peek`, `_placeTermPeek()`): the real terminal, clipped and shifted, never a copy of text and never resized. Hidden by its own button it has no window (`.peek-off`). The side panels end above it (`--below-bar`).
- **A terminal is never restarted by a rebuild**, since it forks the shell as its own child. NixOS: `restartIfChanged = false`. home-manager: `X-SwitchMethod = keep-old`. nix-darwin has no such switch, so the job contains no store path and no setting: it runs `/run/current-system/sw/bin/eznix-terminal-start` (a script holding port, key file, folder and shell), and `postActivation` copies its plist into `~/Library/LaunchAgents` and loads it only when it is not loaded (`terminalPlist`). Don't put anything that varies per build into that job. The page offers a restart when the running terminal differs: one checksum (`STAMP`) over its program file and how it was started; `_terminal_for()` in the server computes the same from the installed program and `[terminals.NAME]`, so those must be exactly the arguments the module passes; the ping carries only the answer, `terminal_stale`. The terminal's package has no version in its name (`packages.nix`). Any change to `eznix-terminal.py` makes every installed terminal offer a restart.
- **macOS logs** are in `~/Library/Logs` (`eznix.log`, `eznix-terminal.log`), not `/tmp`.

## The page and the server

- **Page checksum** (`_compute_page_hash()`, `PAGE_HASH`): one hash of the rendered page (so every setting in it), every file under `webroot/`, user themes and plugins, and `eznix.py`. `/api/v1/ping` reports the current one; a page seeing another reloads, at once if nothing is unsaved, otherwise as soon as that is true (`_updateDirty()`). Autocomplete data is left out and has its own stamp. Polling, not `EventSource` (a reconnecting one wiped Chromium's cookies for the origin).
- **Caching:** the page, stylesheets and scripts are `private, no-cache` with an ETag that is a checksum of the file (`_unchanged()`, `_send_validator()`): a 304 while unchanged. Never address-with-a-checksum caching. API answers are `no-store`. Answers say HTTP/1.1 (`protocol_version`): Chrome re-fetches a page sent as HTTP/1.0 on every load. Connections are kept open after a GET/HEAD answer that went well and has a `Content-Length`; a POST, an error or a refusal closes (an unread body would be read as the next request).
- **Nothing is shown until the page is whole** (`booting` on `<html>`, removed at the end of `_init()` or after three seconds).
- **The page starts with one request for all the files** (`/api/v1/files?content=1`) and asks for the suggestions at the same time.
- **Sessions:** a random token in `eznix_session`, stored hashed in `<state>/sessions.json`. `days` unset (default): the login ends after 15 minutes without a page ping (`SESSION_IDLE`) and a day after login at the latest. Set: that many days (400 at most), no idle limit; `renew` counts from the last page load. Settings are under `[session]` (`session.*` in the modules).
- **`debug`** (`services.eznix.debug`, `debug` in `eznix.toml`, `--debug`) is the one switch for what is only worth knowing while looking into something: `_debug(line)` in the server, `api.debug()` for a plugin, `eznix.debug(...)` in the page. Add a call wherever one helps. Never a secret in such a line. The terminal program has no part in it.
- **The icon is drawn by the server** (`_favicon_svg()`, `/favicon.svg?theme=NAME`): the logo in the theme's `--logo-1` and `--logo-2` read out of its stylesheet, `var()` followed. The manifest names two icons: the bare logo (`"any"`) and a filled one (`"maskable"`, `?filled=1`). PNGs (`_logo_png()`, `/icon.png?theme=&size=&filled=`, 180/192/512, hand-rasterised with `zlib` and `struct`) exist for iOS's `apple-touch-icon`; **the manifest does not list them** (a transparent PNG gave installed Chrome apps a white plate). The logo geometry is in three places: `_LOGO_SVG`, the PNG code, `terminal-panel/terminal.js`.
- **The window bar has the header's colour** (`_loadWindowColour()`, the `theme-color` tag, `theme_color` in the manifest). The tag is never empty: it ships with the configured theme's colour and the first script puts in the last one this browser had (`eznix-window-colour`).
- **The login page** (`webroot/login.html`) is the logo, "eznix (hostname)", two fields, and the button. The fields are the one place not in the theme's font (Chromium styles autofill in its own font). No username is filled in or offered, whoever could log in.
- **Where eznix is reached** is dnsmasq's and Samba's model: `interfaces` (list of interface names) and optionally `listenAddresses`. One socket per interface/address, tied to the interface (`_bind_to_interface()`: `SO_BINDTODEVICE` on Linux, `IP_BOUND_IF` on macOS), so a firewall is not what keeps other networks out. `lo` is an interface like any other and the default `[ "lo" ]`; `[ ]` is every interface; with addresses and no `interfaces`, the default is `[ ]`; a written `interfaces` is used as written. A missing interface is left out with a log line as long as another is. IPv4 only. On NixOS `openFirewall` is refused unless told where (`interfaces` written, or `listenAddresses`). Nothing is kept for compatibility with the old `listen`/`interface`.
- **`certNames` is filled in by hand** for names eznix cannot know; it takes the machine's host names (`hostNames`) and `listenAddresses` itself. The certificate names only what it is told; the options' descriptions say so, and they are the documentation that matters. No lookup of the machine's addresses.
- **Login:** system passwords are built in (`users`; PAM in-process or `auth_helper`). Any other way is a plugin calling `api.login(check, user)`; the `password` plugin is the one configured password. System login is on when `users` is set or no plugin brought a login; eznix refuses to start if nobody could log in. System-password login does not work on non-NixOS Linux through nixpkgs' PAM (it cannot read Debian's `/etc/pam.d`), so the home-manager module refuses `users` and asks for `passwordFile`/`password`.
- **No `flake.nix`, no new files** (`hasFlake`, `_flake_there()`, `flake` in `/api/v1/files` and every ping): the empty page says there is no flake and has no menu, no New file/folder/Import, drops are refused, and files that are there anyway open with a notice. General, not install mode's. The bottom-right notices are the page's (`.notices`, `.notice`), a box of no height right above the terminal's slot or the status bar.
- **A button that is waited on is marked** (`.needs-attention`: accent colour, a dot, a tooltip): the terminal's Restart while stale, Autocomplete while there are no suggestions, a tab with a disk conflict.

## The editor

- **Nothing touches disk until Save**, including deletes, renames and moves (`pendingFsOps`, replayed in order). Undo is one global stack of full-state snapshots and survives a reload. After every Save `_rebaseHistoryOnDisk()` tells each other point what is on disk now. Undo never changes the disk. No folder delete is ever queued.
- **What changes on disk shows in the page** (`_followDisk()`, `_files_stamps()`): the ping carries one checksum of the files folder; the page then reads only files whose stamp it does not have. The disk's version counts like a Save; a file with unsaved changes keeps them and is marked until Save or Reload. A Save sends the stamp it expects (`expect`, 409 on a mismatch). Nothing is followed while a fs op waits for Save.
- **A path goes on inside what is switched off:** a disabled option or section is stored as `{_disabled, _value}` and drawn as its value, so every path passes through a wrapper (`_enabledValue()`, `getAtPath()`, `_holderOf()`, `traverseForSet()`, `_contentAt()`, `_setContentAt()`). Merging follows the same rule (`_mergeOrReplace()`); the result is switched off if either side was.
- **In Nix text a disabled entry is comments** (`jsonToNix()`, `_nixParseAttrs()`): Convert to Nix writes it as its setting commented out line by line, and the parser reads a run of such comments back as settings, switched off. Other comments are skipped and lost when converting to native.
- **Suggestions are parsed by their form, never by an option's name:** a path part in angle brackets is a placeholder (`_isWildcard()`), a quoted part is one part (`_pathParts()`), a set is recognised by its type text (`_setEntryType()`, `_typeAt()`), a dot after a set belongs to the name only where the entry is certainly plain (`_isPlainType()`). `checkOptionParsing()` in the browser console runs every loaded option through all of it; run it after touching any of this, on both NixOS and nix-darwin data.
- **Values to choose from** come from `choices.json`, written by the generator (`write_choices()`): `{values, expr, free}`; the page shows any option found there as a dropdown or chips (`choicesFor()`, `nameListFor()`) and names none. A new kind of list is an entry in the generating plugin, nothing in the page.
- **Suggestions are never generated automatically**: the user runs `eznix-autocomplete` (the header's Autocomplete button types the command into the terminal; it is part of `terminal-panel/`, so there is none without a terminal). With none yet (no `.json` in the folder, as after an import) the page marks the button and says so once in the status line, going by `autocomplete_stamp` of 0 in the ping. Of several configurations the generator takes the one named like the machine (home-manager `user@host` or `user`), else the first, also when the machine's own options do not evaluate (`pick_options()`); a host named on the command line has no fallback. Options that are not `visible` are left out. The icon turns while it runs (`.generating` holds a process number).
- **Adding has no button.** Lists have "Add item…" on their menu and items' menus, an empty list has a "Add item…" placeholder, an object in a list also has "Add item like…" (`_blankLike()`), a section/object/file has "Add option…" (`_addMenuItems()`). What is added goes by one rule (`_rowUnder()`, `_newKeyPlace()`, `_putNewKey()`): after the last option that starts above the pointer, first if the pointer is above them all. `_addLineFor()` says whether an Add line is there: always, except where every listed option is set and the object certainly takes no others (`_takesOnlyDeclared()`; anything unreadable counts as free-form). A path the suggestions don't know is never refused: Enter brings up the bar asking for the value's kind (`doAdd()`, `doForceAddWithType()`), also for a new entry of a set that leaves open what it holds (`_saysNoKind()`).
- **A set of plain entries adds and renames in its rows** (`_makeTable()`, `.kv-add`): a set whose entries hold no further names (`_freeEntryType()`) has a last row with an empty name. Renaming an entry is from the right-click menu only, never a click on its name (`_startKeyRename()`, a field laid over the name in the same font so nothing moves).
- **Expressions are completed by the name before the cursor** by the `nixedit` plugin (`_EXPR_NAMES`, `_exprCompletions()`): `pkgs.` and `config.` names, options under the field's own path, values from `choicesFor()`, with help under the pointer (`_nameAt()`, `_helpFor()`). Nothing else of Nix is read (no `with`, `let`, arguments). A new source is an entry in `_EXPR_NAMES`.
- **Menus.** A right-click brings up the menu of what is under the pointer (`_onRowItself()`): an option's for the text of its name or value (the name is `.tt-anchor`), the container's for empty room in the row. A drag goes by the same rule (`_nameText()`, `_besideNameIn()`). Every menu is laid out by `_menu()`/`_MENU_GROUPS`, in one order with a line between groups: `add`, `item`, `convert`, `clipboard`, `view`, `transfer`, `disk`, `restore`. An entry ends in "…" when something more is asked for (a dialog, a name, the cursor in a new field); no "a"/"the" in a placeholder.
- **Copy and Cut also fill the computer's clipboard** (`copyPath()`, `_asImportText()`, `_toSystemClipboard()`) as JSON wrapped in the sections it lies in, which is what Import takes.
- **Lists:** nothing removes an item by itself (Backspace in an empty plain item, or Delete on the menu); an item just added and left untouched stays.
- **A section holding only one sub-section is drawn as one with it** (`renderSection()`, `compactLevel`, 1 unless set, 0 for none): the heading is the whole chain; Delete, Disable, Copy, Cut, Convert and drag act on the chain, Rename edits the dotted name (`renameChain()`), each section above the last has "Add option to NAME…".
- **Sections start folded from `collapseLevel`** (null = nothing folded; top level is 1; the old `sections` setting is read as 3 or unset).
- **Tabs can be ordered** (`_tabOrders()`, `_tabSort()`, `services.eznix.paths.PATH = { order }`): lowest first, no number counts as 100; a folder among folders, a file among files; PATH is the tab's path as shown. A path that matches nothing is ignored silently.

## Layout and themes

The editor's layout is boxes and rows, with the numbers in the themes. Read the comments in `style.css` before changing any of it: most of what looks adjustable was tried and taken back. Edit that file by exact strings (a block of rules was once lost to an edit that replaced "everything between two comments").

- A top-level section is a card. What is in it is a stack of boxes, each with a line along its top and the same padding above and below (`--card-gap`): a sub-section is one, and so is a run of plain options (`.field-group`, made by `renderObj()`, invisible to drags; no rule looks at what is next to what).
- Inside a box everything is a row of `--row-height` (24px) with its text 4px from the top. Rows follow each other with nothing between. A value is 8px from its strip's left and right edge and 4px from its row's top. An object in a list is a box of its own in the section's colour.
- The indent is `--indent-step` (2ch) per level and a setting (`indent`, `indent_level`); a section's options go by its arrow (`_setNestDepths()`, `arrowLevel`, `arrowInline`): under a section with an arrow when open they start where its name's text does, under one without one step in. A section's name and an option's name at the same level always start in the same column. Arrows hang outside the text and never move it (a top-level arrow is two characters before its name). A folded section has ▸ at every level, an open one ▾ from `arrowLevel` (3 unless set, 0 for none). The page never changes when the mouse only moves.
- Below level 2 a section has no line, box or shade of its own, only its indent.
- All eight themes set the layout variables to the same values; a theme may draw lines through `--card-border` and `--value-border`. Sections and bars are one colour in every theme. A theme that copies a desktop is made from a screenshot of its file manager (`THEMES.md`).
- The theme a browser starts with follows the system eznix runs on, set by the modules (`defaults.theme`): `osx` on macOS; on NixOS `breeze` with Plasma or `gnome` with GNOME when that is the only desktop, else `nixos`; home-manager `nixos`.

## The system plugin: import, export, backup

- **A system import takes only a zip of a system**: `flake.nix` at its top, as an export has. Any other is refused before anything is touched (`prepare()`). It is all or nothing: what would be written or removed is worked out first, identical files are left alone, and if eznix may not change any one, it refuses before the snapshot and the first write.
- **`protect`** (default `[".git"]`) is the machine's alone: never exported, backed up, written or removed. An import or restore replaces the whole system and leaves only what `protect` names; the backup taken first holds every file it removes. **`exclude`** is what an export leaves out, nothing more. Both read like `.gitignore` lines through `api.ignore()`. The default `exclude` keeps `hardware-configuration.nix` out. Links are never followed, a path out of the flake is refused, there are size limits (100,000 entries, 2 GiB unpacked, 1 GiB per file by declared sizes).
- **An import is asked about first** (`dry=1`, `run_import()`, `check()`): the page's dialog (`_askImport()`) shows what is `kept` and `removed`, a zip without `flake.nix`, the files of `generate` that will be missing, and each command that will run (that is the consent). On the installer (`mode = "install"`) nothing is asked.
- **`generate`** is a list of `{file, command}` that makes files an imported system lacks, typed into the terminal after the import. No defaults: an entry needs both or is ignored. The zip can carry the list (`services.eznix.plugins.system.generate` in its configuration JSON), the running configuration's is used only when the zip has none. A file that is there, or one the zip brings, is never made. After an import or restore that changed anything the suggestions' `.json` files are removed (`forget_suggestions()`) and the page marks Autocomplete.
- **`open`** lists paths of the imported system to open (a template's `README.md`), read from the zip's configuration like `generate`, from any zip since it runs nothing.
- **`sources`** are places systems can be imported from: a zip (every folder with a `flake.nix` is a system) or a JSON index of zips, folders and indexes; https or a local path, cached ten minutes in `system-sources/` and used as a fallback; only a location a listing of the setting reached is ever fetched. `NAME.json` beside `NAME.zip` (or `info` on an index entry) gives `{name, description}`. An index entry with a `path` is listed without fetching. A refresh makes the kept copy out of date. The page shows one card per source (`_sourceCard()`, `showSystemCards()`).
- On NixOS the flake is group-writable for `eznix` by default (`flakeWritable`): group and mode only, owners untouched (git and Nix refuse a repo owned by someone else), dot-folders skipped. It gives the service nothing it didn't have: a JSON file it can write can hold any Nix expression, built as root.

## Plugins

**A plugin is something that needs nothing from the system eznix runs on.** The terminal is therefore part of eznix (server side in `eznix.py`, services in the Nix modules, options at the top level) and only its page code lives apart in `webroot/terminal-panel/`, loaded like a plugin's files (`TERMINAL_PANEL`) and reached through the same events. Don't turn features that need a service into plugins. Core, not plugins: the terminal, Save, ordinary import/export of files, file backups on save, themes (plain CSS anyone can install without trusting code), and support for each system.

A plugin is a folder with `plugin.json`: `{"name", "styles": [], "scripts": [], "server": "x.py"}`, all but the name optional. Found in `plugins/` and in `plugins_dir` (`_load_plugins()`); `[plugin.NAME]` in the config holds its settings, `enabled = false` leaves it out. The interface may change freely.

- **Page side:** scripts load after the page's own and before `_init()`, sharing its global scope. The page reaches a plugin only through `eznix.emit()` events (`init`, `ready`, `render`, `dirty`, `theme`, `ping`, `open`, `run`, `terminal`) and `eznix.addButton()`, documented at the top of the main script. The page must never name a plugin's function.
- **A plugin looks like the page:** it uses the page's classes (`.btn`, `.modal`, `.modal-input`, `.modal-hint`, `.modal-error`, `.autocomplete-list`...) and the theme's variables; its own stylesheet holds only what the page has no rule for.
- **Server side:** `setup(api)` registers handlers under `/api/v1/plugin/NAME/` (`PluginApi`: `api.get/post`, `config`, `flake`, `state_dir`, `page`, `login`, `ignore`, `debug`). A handler returns JSON-able data or `api.Download` and raises `api.Error(status, message)`. Core checks the login first. A plugin whose server file fails to load is left out whole.
- Each shipped plugin has a `README.md` for users with a table of every setting, in the layout of the main one; the main README's Plugins section links to them. Update it when a setting changes.
- **Side panels are the page's** (`eznix.sidePanel()`): a plugin's panels are tabs along the top of one window per `group`; the windows stand side by side over the right part of the editor, sharing its width, the left edge dragged. The side is fixed in the window, from under the top bars to the terminal's row of buttons, and does not follow the editor's height. Where the open terminal and the side overlap the last pressed is in front (`.side-front`; the tab bar is z-index 32 and the header 33 for that). They slide away on a press outside (`autoHide`/`auto_hide`, on by default) and a button on the side's top left corner brings them back.
- **`files`** is menus of the flake's files by kind: each `[plugin.files] menus` entry is a button with `name`, `extensions` and `command`, opening a file in a terminal of its own as a side tab (`openFlakeFile()`). Default: one "Nix files" menu for `.nix`. The command is the menu's, else `editor`, else `$EDITOR`, then nano. Each line ends in a cross that deletes the file after a question; the tab's cross closes it by hanging up on the program. "New file…" makes nothing itself (the program makes the file on first write; a missing folder is made by `mkdir -p` in front of the program for that open only). Not rebuilt: an editor of its own in the page, or a shipped editor (`ezedit`): the user wants an editor set up in Nix.
- **The generator's plugins** (`kernels`, `homebrew`, `home-manager`): what only some systems have is a plugin, not a branch of `eznix-autocomplete.py`. `plugin.json` names a file as `"autocomplete"` with `generate(ctx)`, `SYSTEMS` and `OPTIONS` (documented above `find_plugins()`). `all` runs every plugin that applies; a command named after a plugin runs that one; a plugin that raises is skipped, one that calls `ctx.failed()` leaves its file as it was and ends the run with an error. The generator finds plugins in `plugins/` beside `bin/` (the Nix package passes `--plugins-dir`) and `plugins_dir`, and honours `enabled = false` through `--config`. This is an exception to "a plugin needs nothing from the system": they are for one system each and have no service. `optionSearch()` skips an option with a placeholder before its last part, so the home-manager plugin adds the `home-manager.users` entry itself.

## Nix

`nix/options.nix` holds the options and builds `eznix.toml` from them with `pkgs.formats.toml`; each module (`nixos.nix`, `darwin.nix`, `home.nix`) passes it its own paths and adds only the services. NixOS is the service design (account `eznix`, a terminal unit per user in `users`); macOS and home-manager are for one person: two agents/user units running as them.

- **eznix installs nothing in the folder it edits.** `lib.jsonDir DIR` (or `{ dir, exclude }`) is a function; a module can't pass its option to it (reading `config` there recurses). `exclude` exists twice and the two must agree: the function's argument keeps a path out of the build, the editor's setting (`_excluded()`) keeps it from being a tab. Entries are read like `.gitignore` lines (a name at any depth, `/name` anchored, `* ? [a-z] **`, `!entry`, last match decides); each side turns an entry into a regex by the same steps (`_exclude_rule()` in `eznix.py`, `nix/exclude.nix`), and `test/exclude.json` is one table of cases both run against (`test_server.py`, `checks.exclude`): add a case when touching either.
- **HTTPS** is one switch, `enableHttps`: on by default when `listen` isn't local or a `cert` is given. With no `cert`/`key`, eznix makes a local CA and certificate in the state folder. With a certificate, plain HTTP on the same port gets a redirect to https (`_redirect_to_https()`: the first byte of a connection says which it is). The reverse (https redirecting to http when HTTPS is off), and a second port for plain HTTP, were built and reverted because the page hung: don't build them again. `trustCert` (off by default; the authority has no name constraints, so trusted it could vouch for any site) adds the CA to the machine's browsers as the person concerned (`trustCertScript`: a oneshot unit per user on NixOS, the editor's `ExecStartPre` on home-manager, `sudo -u` in the activation on macOS); read the comments there before touching it.
- **eznix in the application menu** comes from the configuration (`programs.eznix`, NixOS and home-manager): an entry opens its address in the default browser (`xdg-open`), named for its address ("eznix (https://host:port)"); `apps` adds an entry per other machine. Not built, on purpose: having the entry install a browser app (browser policy, `WebAppInstallForceList`), or a window program of eznix's own, just to make the browser's download bubble visible.
- **Templates** (`templates/darwin`, `nixos`, `home`): a `flake.nix` and one JSON file with eznix on. The configuration is named `default` in each, so every rebuild command carries `#default`. The NixOS one imports the installer's `configuration.nix` and adds eznix beside it. The macOS one sets `nix.enable = false` (Determinate Nix). All build on the stable release (nixpkgs and, where there is one, the branch of nix-darwin or home-manager that goes with it), named in each `templates/*/flake.nix`, in `flake.nix` (its own nixpkgs and the first-switch commands in `welcomeText`) and in the README's first-switch commands: **raise it by hand when a release comes out, in May and November**. There is no `flake.lock` in the repository on purpose, so `nix flake init -t` prints a harmless "not writing modified lock file" and running or building straight from GitHub needs `--no-write-lock-file`. The one thing to fill in is `YOUR-USER-NAME` (an assertion in `options.nix` catches it left in). They name `github:kalken/eznix`, so they are only as new as what is pushed; to try one against the checkout use `--override-input eznix path:.`.
- **A buttons/menus `description`** is the tooltip's first line (`_buttonTip()`).

## Known gaps

- A slow reconnect after a rebuild was seen on one router and not explained; a ping is given up after three seconds (`PING_TIMEOUT_MS`).
- Not tried on real machines: GNOME and the `breeze-light` themes against a real desktop; several template/platform combinations beyond the ones the README's Quick Start was run on.
